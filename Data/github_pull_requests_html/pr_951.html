debian: add initial Debian packaging (.deb build)

Pull Request #951

Description

This PR adds a `debian/` directory for building auto-cpufreq as a proper `.deb` package on Debian/Ubuntu systems. ## Approach - Minimal, self-contained `debian/` directory — zero changes to existing code - Python package installed to system site-packages via dh_install (no venv) - Depends on system Python packages (python3-psutil, python3-click, etc.) - Wrapper scripts at /usr/bin/auto-cpufreq and /usr/bin/auto-cpufreq-gtk - Systemd service, polkit policy, desktop file all shipped with the package - Scripts also installed to /usr/local/share/auto-cpufreq/scripts/ for compatibility with auto-cpufreq --install (SCRIPTS_DIR in core.py) ## Tested - `dpkg-buildpackage --no-sign -b -d` produces a working .deb (102 KB) - Installed and tested on Debian unstable (forky) - Service starts, binary runs, GUI launches via auto-cpufreq-gtk ## Files | File | Purpose | |------|---------| | debian/control | Package metadata and dependencies | | debian/copyright | LGPL-3.0+ licensing | | debian/changelog | Initial version (3.1.0-1) | | debian/rules | dh with manual wrapper install | | debian/install | File mapping | | debian/postinst, postrm | Systemd service lifecycle | | debian/auto-cpufreq.service | Systemd unit | | debian/auto-cpufreq.sh, auto-cpufreq-gtk.sh | Python wrappers | | debian/source/format | 3.0 (quilt) | | debian/.gitignore | Excludes build artifacts | ## Maintainer Happy to maintain the Debian packaging going forward. Existing installer, Snap, Nix, AUR, and other packaging methods are untouched.

filhocf:

Thanks for the detailed report — I've fixed it. The root cause: `is_running()` in `core.py` only matched the hyphenated binary name `auto-cpufreq` in the process cmdline. The .deb wrapper starts the daemon via `python3 -m auto_cpufreq.bin.auto_cpufreq --daemon`, so the cmdline contains the module name `auto_cpufreq` (underscore), and the check missed it — even though systemd shows the service active. In the official install the daemon runs as `/opt/.../bin/auto-cpufreq --daemon`, which is why it only broke in the .deb. The fix makes `is_running()` also match the Python module name (`auto_cpufreq`), so detection works regardless of install method. I verified both launch paths (hyphenated binary and `python3 -m`) plus negative cases — all pass. `--stats` now correctly reports the running daemon. Commit `36dd266`.

@filhocf okay, I can confirm I can install the package with latest changes and auto-cpufreq daemon will be running. However there are few things that will need to be changed before this can be merged, as it introduces quite some breaking changes. **1. auto-cpufreq daemon should not be automatically installed as soon as .deb package is installed** Right now after I install e.g `auto-cpufreq_3.1.0-1_all.deb` file, `dh_installsystemd` will find and install the systemd unit file `/usr/lib/systemd/system/auto-cpufreq.service` and it'll enable and start service auto-cpufreq systemd service automatically and `sudo auto-cpufreq --stats` will be available. But this is not the intended flow and will interefere and break things. After auto-cpufreq is installed with e.g: [auto-cpufreq-installer](https://github.com/AdnanHodzic/auto-cpufreq#auto-cpufreq-installer), `auto-cpufreq` becomes available as a binary, and user has all options listed with [auto-cpufreq --help](https://github.com/AdnanHodzic/auto-cpufreq#auto-cpufreq-modes-and-options) at their disposal. Maybe they want to run --monitor or --live first before they run --install. Don't enable & start auto-cpufreq daemon (option 1)** To have intended behavior we should have empty override for dh_installsystemd, and debian/rules could be as simple as: ``` override_dh_installsystemd: # Do nothing: let auto-cpufreq --install handle service registration ``` This way, dpkg -i installs the wrapper binaries and files (including auto-cpufreq.service into `.../share/auto-cpufreq/scripts/`) but no systemd services are enabled or started during package installation. The user must manually run: `sudo auto-cpufreq --install` which executes auto-cpufreq-install.sh to copy the unit to `/etc/systemd/system/` and run `systemctl enable --now auto-cpufreq.service` and e.g `sudo auto-cpufreq --remove` will remove and disable it. **3. Don't enable & start auto-cpufreq daemon (option 2)** Install the systemd unit into system directories without starting or enabling it and let Debian package manager to the heavy lifting, e.g register the unit file in `/usr/lib/systemd/system/auto-cpufreq.service`, but not enable or start it automatically: In debian/rules, pass `--no-enable --no-start`, e.g: ``` override_dh_installsystemd: dh_installsystemd --no-enable --no-start ``` In this case after user runs `sudo auto-cpufreq --install` then service would be enabled and started. In both cases, I think it's useful for user to see output that's displayed when you run e.g `sudo auto-cpufreq --install` as shown above, as it gives user a lot of useful info, on what happened and etc ... **4. GNOME Power Profiles should be stopped, which is not the case with .deb right now** As you can see in output from --install above, this service will be disabled, as [mentioned in README](https://github.com/AdnanHodzic/auto-cpufreq): > When installing auto-cpufreq via [auto-cpufreq-installer](https://github.com/AdnanHodzic/auto-cpufreq#auto-cpufreq-installer), if it detects the [GNOME Power Profiles service](https://twitter.com/fooctrl/status/1467469508373884933) is running, it will automatically disable it. Otherwise, that daemon will cause conflicts and various other performance issues. You can check its status by running auto_cpufreq.power_helper script, e.g: `sudo python3 -m auto_cpufreq.power_helper --gnome_power_status` from auto-cpufreq, and you can even disable it by running: `sudo python3 -m auto_cpufreq.power_helper --gnome_power_disable` For full list of options run: `sudo python3 -m auto_cpufreq.power_helper --help` Also it shouldn't be possible to run `--live` after `--install` as then you have 2 duplicated processes doing the same thing, #953 is working on fixing this issue, as it seems [this feature got lost along the way](https://github.com/AdnanHodzic/auto-cpufreq/pull/953#issuecomment-5300994829). **5. auto-cpufreq source code should not be in /debian** Finally, auto-cpufreq source code should not be in /debian, but other way around, debian/ should simply be a dir under, e.g: `auto-cpufreq/debian` Excellent guide for this which I also followed when I created my first Debian packages is [Debian New Maintainers' Guide](https://www.debian.org/doc/manuals/maint-guide/) and it clearly outlines [Required files under the debian directory](https://www.debian.org/doc/manuals/maint-guide/dreq.en.html). Hope this clarifies some things and helps you make the changes the right way, looking forward to any updates you may have!
