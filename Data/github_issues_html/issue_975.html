Add verified versioned source installs and release updates

Issue #975

Description

## Summary This PR makes source installations versioned and verifiable, and changes the built-in source updater to install published release tags instead of the development `master` branch. It also makes prerequisite, installer, updater, and service-manager failures explicit so a failed operation is not reported as a successful installation. This supersedes the broader recovery-snapshot implementation previously published in this PR. The current design is intentionally narrower: it protects the installed source tree through separate release generations and keeps the existing daemon behavior, with only the lifecycle changes needed to propagate failures and make install/remove retries safer. Earlier inline review threads that refer to files no longer present in the diff describe the previous implementation. Related to #973: the package-manager problem reported there is external to auto-cpufreq, but it exposed that installer failures could be ignored and leave wrappers pointing to an unusable environment. ## Source installation The source installer now: - stops immediately when distribution dependencies, Python, venv creation, pip, PyGObject/GTK, or package installation fail; - consistently selects the distribution Python associated with system PyGObject packages; - handles Debian/Ubuntu derivatives, Fedora/RHEL, Arch-based distributions, openSUSE, Void, and Solus, while keeping unsupported distributions on an explicit manual path; - uses command-scoped Git `safe.directory` handling instead of leaving a persistent trust exception; - supports Git checkouts and source archives carrying Git archival metadata; - rejects builds whose exact source revision or version metadata cannot be established. GitHub-generated source archives can therefore be used by releases published after this change is included. Existing release archives are not modified retroactively. ## Versioned installation layout Each candidate is built directly in a new directory under: ```text /opt/auto-cpufreq/releases/. ``` The candidate receives its own virtual environment and version-specific resources. Before activation, the installer verifies its Python environment, dependencies, CLI entry points, package version, and completion marker, and records the exact source revision. Only a complete candidate can become active. Activation atomically replaces: ```text /opt/auto-cpufreq/current ``` The public wrappers and service files refer to `current`, so an incomplete candidate does not replace the working generation. If the final public-command verification fails, the installer attempts to restore the previous active generation and wrapper. Previous complete generations are retained until the source installation is removed. The source installer also refuses to replace the source tree while the auto-cpufreq daemon marker is present. This keeps daemon removal tied to the generation whose lifecycle helper installed it. ## Stable source updater For source installations, `auto-cpufreq --update` now: 1. reads the latest published release tag; 2. fetches that exact fully qualified tag into a unique staging directory; 3. installs it through the versioned source installer; 4. reinstalls the daemon only when it was installed before the update; 5. verifies that the public command reports the selected release. It does not update from `master`. Snap and AUR installations remain owned by their package managers. If daemon removal, download, installation, daemon reinstallation, or final version verification fails, the updater returns a failure instead of announcing success. When installation fails after removing an existing daemon, it attempts to reinstall that daemon from the active source generation. ## Daemon lifecycle changes The daemon install/remove scripts remain close to the existing project structure, with focused safeguards required by the updater and versioned layout: - service-manager command failures propagate to the CLI; - repeated removal can continue after already-completed steps; - required legacy s6 commands are checked before service files are deployed; - systemd removal verifies that the unit still matches the managed unit before deleting it; - systemd removal remains successful when disabling the service unloads the unit; - service and PolicyKit paths resolve through `/opt/auto-cpufreq/current`. This PR does not add a persistent host-state snapshot system or a new daemon-lifecycle framework. ## Documentation and packaging The README now distinguishes: - stable installation from a release source archive; - development installation from a Git checkout; - stable release updates through `auto-cpufreq --update`; - complete source removal versus daemon-only removal. Git archive metadata, strict dynamic versioning, Nix's explicit version bypass, and full Git history in the Linux build workflow keep version resolution consistent across Git, release archives, CI, and Nix builds. ## Validation The final tree was validated with: - a complete legacy-to-versioned source installation on Linux Mint 22.3 with systemd and Python 3.12; - daemon install, remove, and reinstall cycles; - restoration of `power-profiles-daemon` and Bluetooth boot behavior during the tested daemon round trip; - preservation of `/etc/auto-cpufreq.conf` during source installation and daemon lifecycle tests; - correct installed release and Git revision reporting; - an up-to-date updater no-op that preserved the active generation and daemon PID; - targeted failure, retry, wrapper rollback, version-selection, and service-manager regression harnesses used during development; - syntax/compile checks for every commit in the consolidated series; - `git diff --check`; - `bash -n` for the installer and daemon lifecycle scripts; - `python3 -m py_compile` for the changed Python modules; - `patch --dry-run --fuzz=0` for the Nix patch; - GitHub Actions Linux Build and Nix Flake workflows. No temporary regression harness or permanent test infrastructure is included in the PR. ## Commit guide 1. `feat: bootstrap portable source installations` 2. `feat: activate verified versioned source releases` 3. `feat: update source installs from verified release tags` 4. `fix: make daemon-aware updates fail safely` 5. `fix: make activation and daemon cleanup retryable` 6. `fix: preserve updater lifecycle and staging state` 7. `fix: preserve daemon manager state during lifecycle changes` 8. `fix: enforce reproducible versions across source builds` 9. `fix: report derivative distribution versions correctly` ## Scope This PR does not add a new installer frontend, modify Snap/AUR update ownership, introduce a permanent test framework, or refactor unrelated power-management policy.

Hi @AdnanHodzic, I reworked the implementation rather than continuing to extend the previous recovery-snapshot design. The review findings, together with reproducing several failure paths locally, showed that the earlier approach was becoming broader than necessary for the source installer and updater problems this PR is intended to solve. The PR is now down to 9 commits and 18 changed files. The persistent recovery-snapshot modules and related lifecycle abstractions have been removed from the diff. The replacement design keeps source-install safety at the installation boundary: each source installation is built as a separate verified generation, and `/opt/auto-cpufreq/current` is switched only after the candidate has passed verification. Source updates now install exact published release tags rather than `master`. Daemon changes are limited to the failure propagation, retry behavior, and managed-service ownership checks needed to support that flow. Because a substantial part of the previous implementation no longer exists, GitHub now marks the corresponding inline review threads as outdated. I reviewed the underlying failure modes against the replacement implementation and addressed those that remain applicable to the current design. I also rewrote the PR description to document the current implementation and its narrower guarantees. The final tree was tested on Linux Mint 22.3, including migration to the versioned source layout, daemon install/remove/reinstall cycles, and the updater’s up-to-date path. The PR is ready for review. Thanks again for the feedback.
