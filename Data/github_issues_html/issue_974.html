lucasleocs:

@AdnanHodzic I took a closer look at this because there seem to be a few separate things happening here. The Zorin Power Mode disappearing while auto-cpufreq is installed is actually explainable: when the daemon is installed, auto-cpufreq disables and masks `power-profiles-daemon` to avoid having two power managers controlling the same settings. Since the desktop Power Mode UI depends on PPD, the selector disappearing is expected in that state. However, I noticed that the current removal path does not really restore the previous host state. It mostly re-enables PPD/TuneD using a fixed policy instead of remembering exactly how they were configured before auto-cpufreq was installed. This is one of the things #975 changes: it snapshots the original PPD/TuneD service state and active power profile before making persistent changes, and restores that state only after the auto-cpufreq daemon has been successfully removed. It also keeps the recovery state if restoration fails. That probably does not explain the ~50 W consumption while auto-cpufreq is running, but it means that comparing "auto-cpufreq installed" with "auto-cpufreq removed" on current master can change more than just auto-cpufreq itself, so the comparison is not completely controlled. There are still a couple of things here that I don't think the current code explains yet. In particular, the report that changing the governor seems to have little effect while the OS power mode does is worth investigating separately. With `intel_pstate`/HWP, `powersave` is not simply a low-frequency cap, and governor, EPP, EPB, turbo and platform profile are separate parts of the effective policy, so seeing the actual values together would help a lot. The missing fan RPM is also interesting. This machine is already on kernel 7.0 and Lenovo's newer WMI Gamezone/Other driver stack has HWMON fan reporting support for compatible gaming systems. That does not guarantee this particular LOQ firmware exposes the required capability data, but I would have expected us to at least be able to distinguish whether the kernel exposes a fan sensor and `psutil` misses it, or whether the kernel exposes no RPM at all. I'm working on expanding `--debug` for exactly this reason. Ideally one debug report should give us the effective governor/EPP/EPB/HWP/turbo state, CPUFreq policies, platform profile/provider, daemon and PPD/TuneD state, exact source revision, and enough HWMON information to tell why a fan reading is missing, instead of asking the reporter to run several additional commands. So at this point I think the issue is real, but I would not attribute the power difference to HWP Dynamic Boost or to a single auto-cpufreq setting yet. There are several policy layers changing at once, plus a few unusual observations on this particular system.

lucasleocs:

@AdnanHodzic I looked into the `Power draw: 0.00 W` behavior more closely, and I found the source. It isn't caused by the changes in #975. However, I realized the misleading `Power draw` display was introduced by my earlier #964 changes. The underlying value comes from the battery's `power_now` sysfs attribute, so it represents power flow through the battery rather than total system power consumption. When the laptop is running on AC and the battery isn't supplying power, `power_now` can legitimately be 0. Once AC is disconnected and the battery starts discharging, the value becomes non-zero again, which matches what you observed. Before #964, the GUI didn't display this value. In #964 I added it unconditionally under the label `Power draw`, which makes it look like system power consumption when it actually isn't. So #975 doesn't appear to have introduced the behavior, but your testing exposed a reporting issue from #964 that I should fix separately.
